## Findings (ranked)

1. **C26: the use case's `handoff` result is unasserted (check FAIL).** AC 27 depends on `AnswerClientQuestionUseCase` returning `handoff: reason` (`src/usecases/answer-client-question/answer-client-question.use-case.ts:169,172`), which the controller reads at `src/infrastructure/external/whatsapp/evolution/evolution-webhook.controller.ts:152-156`. The controller test injects that field itself, and the use-case spec throws away the result of `execute` (`answer-client-question.use-case.spec.ts:144-150`). If `handoff: reason` were dropped from the use case, every hand-off would stop being logged and the whole suite would stay green. To fix it, assert the value `execute` returns in the US-16 use-case tests (for example `toEqual({ outcome: 'sent', kind: 'handoff', handoff: 'requested' })`), or capture the log in the e2e as US-15's C19 did.
2. **C3: seam gap on the failed hand-off log (level).** The e2e proof asserts only `204` and the pause (`test/whatsapp-handoff.e2e-spec.ts:292,294`). The log claim is proven only on a controller whose use-case result is stubbed (`evolution-webhook.controller.spec.ts:337-342`). Nothing asserts that the hand-off branch returns `{ outcome: 'failed', error }` when `sendText` throws (`answer-client-question.use-case.ts:168-170`). A `return NO_REPLY` in that `catch` would pass every test, and the failed notice would go unlogged. This has the same root as finding 1. It is recorded as a gap and does not flip the row, because the claim is about the controller and that is proven.
3. **C18 test titles are mislabelled (cosmetic).** The `%s` in `'CA-16.5 (C18): a pause %s old answers: %s'` (`test/whatsapp-handoff.e2e-spec.ts:480`) takes the second table column (milliseconds), not the boolean, so the output reads "a pause 11h59 old answers: 43140000". The assertions themselves are correct.
